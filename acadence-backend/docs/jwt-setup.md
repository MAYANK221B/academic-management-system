# JWT access-token keys

Generate a persistent local key pair once using OpenSSL, in a directory outside
the repository. Restrict the private file to the account running Acadence (use
filesystem ACLs on Windows). Never commit, print, or share the private key.

```sh
openssl genpkey -algorithm RSA -pkeyopt rsa_keygen_bits:3072 -out acadence-private.pem
openssl pkey -in acadence-private.pem -pubout -out acadence-public.pem
```

The private file must be unencrypted PKCS#8 PEM (`BEGIN PRIVATE KEY`); the public
file must be X.509 SubjectPublicKeyInfo PEM (`BEGIN PUBLIC KEY`). For production,
mount files from a secret manager with restricted permissions. Keys are loaded
once at startup; missing, malformed, weak, or mismatched keys prevent startup.
No keys are generated by application code.

In IntelliJ, open Run > Edit Configurations > the Spring Boot application >
Environment variables. Set `JWT_PRIVATE_KEY_PATH` and `JWT_PUBLIC_KEY_PATH` to
absolute filesystem paths, for example `C:/Users/yourname/acadence-keys/acadence-private.pem`
and the corresponding public file. Also supply `DB_PASSWORD` for PostgreSQL.
Paths are filesystem paths, not `classpath:` or `file:` resource URLs.

Application properties:

| Property | Default / source |
| --- | --- |
| `acadence.jwt.issuer` | `acadence` |
| `acadence.jwt.audience` | `acadence-api` |
| `acadence.jwt.access-token-expiration` | `15m`, must be positive |
| `acadence.jwt.private-key-path` | `JWT_PRIVATE_KEY_PATH`, required |
| `acadence.jwt.public-key-path` | `JWT_PUBLIC_KEY_PATH`, required |

Override ordinary settings through Spring configuration, e.g.
`ACADENCE_JWT_ISSUER`, `ACADENCE_JWT_AUDIENCE`, and
`ACADENCE_JWT_ACCESS_TOKEN_EXPIRATION`. Signatures accept RS256 only. Validation
requires the expected issuer and audience, expiration and not-before claims;
Spring Security's default timestamp validation allows 60 seconds of clock skew.
Keep host clocks synchronized.

`JwtService.generateAccessToken(Long userId)` receives the authenticated database
ID, never the email. The future AuthService must obtain that ID after successful
authentication. Use `getAccessTokenExpiration()` for response lifetime metadata.
Tokens contain only `sub`, `iss`, `aud`, `iat`, `nbf`, and `exp`.

CSRF is disabled for Authorization-header bearer authentication. Revisit it before
introducing cookie-based refresh sessions. JWT validation does not re-read account
status from PostgreSQL: a token issued before disabling an account remains usable
until expiry. Key rotation and revocation policy should be planned before production.

Run the isolated crypto/wiring tests with `mvn -Dtest=JwtConfigTest test`.
They generate temporary keys only in tests; no database or persistent local keys
are needed. Full application startup still requires valid external keys and the
configured PostgreSQL credentials.
